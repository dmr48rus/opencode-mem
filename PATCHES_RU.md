# Что меняет этот форк

Отличия от `tickernelz/opencode-mem` на 2.31.0 — по одной строке на правку:
что делает и зачем понадобилось. `FORK-NOTES.md` объясняет устройство и сборку,
этот файл — список изменений в поведении.

Коммиты апстрима здесь не повторяются. Наши начинаются с `b46a0ca`.

## Оценка и захват

**`b46a0ca` перенормировать гибридную оценку по тем сигналам, что есть** —
`turso/vector-search.ts`, `config.ts`, `auto-capture.ts`, `client.ts`,
`api-handlers.ts`, `opencode-provider.ts`, `index.ts`, `v2/plugin.ts`.
У записи без тегов нет `tags_vector`, но вес тегов всё равно начислялся, и
запись могла перевалить порог и больше не находиться никогда — даже запросом
по её собственным словам. Теперь веса нормируются по фактически присутствующим
сигналам. Одновременно включены префиксы задач для эмбеддингов, потому что с
ними считались уже существующие векторы.

**`954a18a` убрать имя ошибки из всплывающего уведомления** — `auto-capture.ts`.
Отказы писались в лог как `{"error":""}`, когда отклонение SDK не несло
сообщения. `describeError()` пишет имя и строку стека, а в уведомление уходит
только голое сообщение.

**`8b7bd34` одна запись диагностики на попытку захвата и политика повторов** —
`capture-diagnostics.ts`, `capture-retry-policy.ts`, `auto-capture.ts`, два
файла тестов. Перенесено из OMMS. Каждая попытка пишет ровно одну запись, по
которой можно считать, с кодом причины и HTTP-статусом; перманентный отказ
заканчивает ход сразу, а не пролеживает остаток отсрочки. Одно расхождение с
оригиналом: здесь persist-error классифицируется по статусу, потому что наше
хранилище — сервер, где `401` ответит так же всегда, а не локальный файл,
который может быть лишь занят.

## Память на сервере

**`8f4f2ce` + `b91f124` клиент удалённого хранилища** — `remote-storage.ts`,
`config.ts`. Клиент на уровне сервиса, а не драйвер базы: плагин шлёт
sqlite-специфичные запросы, которые нельзя проксировать по REST, поэтому
проксируется набор операций, которые плагин действительно выполняет. Эмбеддинги
считает сервер — именно поэтому клиент может обойтись без локальной модели.

**`199fb50` направить обращения клиента к удалённому API** — `client.ts`,
`api-handlers.ts`, `remote-storage.ts`. Поиск уходит текстом, сервер считает
эмбеддинг; запись уходит содержимым, сервер считает эмбеддинг. Тот же патч
починил `handleAddMemory`, который терял `sessionId`, и авто-захват рвал связь с
сессией.

**`cb59628` проводить миграцию тегов через провайдер OpenCode** —
`api-handlers.ts`. Миграция собирала внешнего провайдера до всякой работы,
поэтому в конфигурации только с OpenCode кнопка не работала ни разу, вместо
того чтобы использовать провайдер, который уже есть у плагина.

## Профиль на сервере

**`1c8a761` `PUT /api/user-profile`** — `api-handlers.ts`, `web-server.ts`.
Upsert, чтобы клиент, которого сервер не видел, тоже куда-то попал.

**`acb8e9f` читать и писать профиль по HTTP** — `user-profile-manager.ts`,
`remote-storage.ts`, `client.ts`, `api-handlers.ts`, `web-server.ts`. GET получил
`raw=1`, чтобы эмбеддинги пережили круг; менеджер ходит на сервер, а не в
локальную таблицу.

**`715bf97` создавать профиль на сервере** — `user-profile-manager.ts`.
Ветка remote была проведена в чтение и обновление, но не в создание, а
создание выполняется ровно один раз на идентичность. Оно падало в локальный
INSERT, который сталкивался со строкой от прежнего локального запуска, так что
каждый раунд обучения заканчивался `UNIQUE constraint failed` уже после того,
как вызов модели оплачен.

## Веб-поверхность

**`e25a296` пропустить API мимо Basic-вызова** — `web-auth.ts`. Пароль охраняет
браузерную поверхность; `/api/*` уходит к проверке токена, которая идёт следом.
Одно требование перед обоими заперло бы собственного клиента плагина в
хранилище, которое он читает и пишет.

## Скиллы

**`f8bbd50` хранить скиллы в общем хранилище** — `skills-manager.ts`,
`remote-storage.ts`. Последнее состояние, оставшееся на этой машине, после того
как память и профиль уехали на сервер. Маршруты `/api/skills` у сервера уже
были, поэтому сервер не меняется, а его локальная база становится общей.
`remoteStorage.enabled` остаётся переключателем обратно на чисто локальную
установку, а `container_tag` перестаёт быть фильтром: общее хранилище глобально.

**Регистрация в OpenCode** — `v2/adapter.ts`. Включённые скиллы подталкиваются
в собственный реестр скиллов хоста при старте и после каждой правки, устаревшие
снимаются, так что скилл из хранилища попадает к модели так же, как файловый. Тег
проекта в фильтр больше не входит — по той же причине глобального хранилища.

Одно место, которое похоже на проектное решение, но им не является: `SKILL.md`
пишется на **всех** путях, включая удалённый. У `Skill.Info` обязательное поле
`path` даже для скилла, чьё содержимое едет инлайном, и этот путь должен
существовать. Строка на сервере остаётся единственным источником истины; файл —
производная копия, которую требует контракт хоста.

Поправка, которую стоит сохранить: в прошлой версии этого файла было написано,
что регистрация не может выполниться, поскольку в `SkillDraft` из
`@opencode-ai/plugin` 1.18.34 есть только `source()` и `list()`. Это SDK
**OpenCode v1**. Адаптер v2 типизирован пакетом `@opencode/plugin` 2.0.24 — тем,
который в этой сборке действительно даёт OpenCode 2.0.28, и там есть
`SkillEditor` с `list/get/add/update/remove`. Ни один скилл здесь не появлялся
потому, что его никто не создавал, а не потому, что регистрация была сломана.

## Репозиторий, а не среда выполнения

**`afd5287` самодостаточный репозиторий** — `dist/` под git (то, что вендорит
сборка, не должно зависеть от пересборки), `remote-mem/` с сервером, а
`eslint.config.js` и `package.json` держат пред-коммит-хук подальше от обоих,
потому что prettier по `dist/` переписал бы тот самый артефакт, который
репозиторий везёт.
