# remote-mem — хранилище памяти для Hermes

Отдельный форк opencode-mem, запущенный как самостоятельный HTTP-сервис без
OpenCode. Хранит память, к которой обращаются сборки Hermes.

## Зачем

Авто-захват и внедрение памяти остаются в плагине (нужен локальный OpenCode для
сводки), наружу уезжает только хранилище. Замеры, на которых стоит решение, —
в `X:\ai\hermes\app\data\opencode\config\FINDINGS.md`, запись от 13.10.2026 (Ф0).

## Запуск

    node server.mjs

Требуется `REMOTE_MEM_FORK` — путь к форку с собранным `dist` (по умолчанию
`./fork` рядом с этим файлом). Остальное — из переменных и конфига:

| переменная        | по умолчанию                      | смысл                                  |
| ----------------- | --------------------------------- | -------------------------------------- |
| `REMOTE_MEM_FORK` | `./fork`                          | корень форка (`dist/` читается оттуда) |
| `REMOTE_MEM_PORT` | `webServerPort` из конфига (4747) | порт                                   |
| `REMOTE_MEM_HOST` | `127.0.0.1`                       | адресbind                              |

Конфиг — стандартный opencode-mem: `~/.config/opencode/opencode-mem.jsonc`.
Ключевые для сервера: `storagePath`, `embeddingApiUrl` + `embeddingApiKey`
(эмбеддинги считает кто-то снаружи — на сервере это отдельный эндпоинт).

## Проверка

    node check.mjs

Поднимает настоящий сервер в изолированном `HOME`, со стабом эмбеддингов, и
проверяет: подъём и ответ `/api/health`, отказ без токена и с чужим токеном,
`/api/stats`, запись через `POST /api/memories`, нахождение записи поиском,
отказ при занятом порте с названной причиной. Код 0 — зелёно.

Стаб эмбеддингов не украшение: `handleAddMemory` вызывает `embeddingService`
(`api-handlers.js:314-318`), поэтому без эндпоинта путь записи не проверяется
вовсе. Проверка заодно доказывает, что удалённый эмбеддинг работает — а это и
есть рабочая конфигурация сервера.

## Что сервис делает и чего не делает

- Поднимает сокет, проверяет занятость порта **до** работы с БД, и отказывается
  стартовать с внятной причиной, а не деградирует.
- Держит цикл событий сам: форк вызывает `server.unref()`
  (`web-server.js:109`), в OpenCode это правильно, отдельным процессом без
  удержателя он завершался с кодом 0 сразу после `listening`.
- Не занимается авто-захватом, профилем пользователя и эмбеддингами: это клиент
  и его настройки.

## Бандл для сервера

    node pack.mjs
    tar -czf remote-mem-bundle.tar.gz -C . bundle     # Windows: bsdtar, в комплекте

    # затем на сервере:
    tar -xzf remote-mem-bundle.tar.gz && cd bundle && ./deploy.sh

**Переносить бандл тарболом, а не через git.** И `fork/`, и `bundle/` стоят в
`.gitignore` — это вывод сборки, — поэтому `git clone`, `git archive` или
worktree-чекаут доставят бандл без форка: контейнер поднимется и упадёт с
«missing dist/config.js». `deploy.sh` начинается со сверки числа файлов `dist`
с `manifest.json`, поэтому называет причину сразу.

`bundle/` содержит сервис, конфиг, `deploy.sh` и форк — `dist` плюс манифесты,
**без `node_modules`**: там лежат win32-бинарники, линуксные сервер ставит сам
первым шагом `deploy.sh`. Пропуск lockfile тоже ожидаем: в вендоренном форке его
нет, поэтому установка идёт через `npm install`, а `--frozen-lockfile` упал бы.
`manifest.json` фиксирует происхождение форка (`patched/2.31.0 @ cb59628`) —
это важно, потому что форк несёт наши правки, и «та же версия» не значит «тот
же код».

Свежий бандль нельзя проверить до установки зависимостей: сервер откажется
стартовать и назовёт причину. Это by design, а не поломка. `deploy.sh` поэтому
ставит зависимости, потом гоняет `check.mjs` на сервере, потом качает модель и
только затем поднимает сервис.

## Развёртывание (Debian 13, x86_64, docker compose)

Требование платформы — **glibc, не musl**: `@tursodatabase/database` берёт
движок из `database-linux-x64-gnu`, а `onnxruntime-node` 1.30.0 тянет свой
glibc-бинарник в postinstall. На alpine установка пройдёт, а первый запуск
упадёт. Базовый образ — `node:22-bookworm-slim`.

    git clone <repo> /opt/remote-mem && cd /opt/remote-mem

    Сервис ставится **сборкой образа**: `docker compose build` печёт форк и его

зависимости в слой, поэтому на хосте не нужны ни node, ни npm, а win32-бинарники
из сборки Hermes не могут случайно попасть в образ. Два `test -d` в Dockerfile
роняют **сборку**, если платформа не дала ни onnxruntime, ни движка Turso, — вместо
того чтобы ловить это на первом запросе клиента.

Единственное состояние на хосте — каталог `./data`: шарды, кэш модели, токен и
копия конфига. Конфиг кладёт на место `fork.mjs` при каждом старте, а не
монтируется файлом: монтаж был источником ловушки, где docker создаёт на месте
файла каталог и конфиг молча не читается. И не entrypoint-скриптом: `--entrypoint`
переопределяется, а миграция запускается именно так — копирование просто не
произошло бы. Переключатель `REMOTE_MEM_INSTALL_CONFIG=1` стоит в образе, а
проверки его не задают: у них своя обвязка со стабом эмбеддингов, и без
переключателя копирование затерло бы её.

Все шаги делает `deploy.sh` из бандла — перечисленное ниже нужно только для
понимания, что он делает:

    # 0. сверка бандла: число файлов fork/dist против manifest.json
    # 1. docker compose build
    # 2. self-check внутри собранного образа (node check.mjs)
    # 3. предзагрузка модели в ./data
    # 4. docker compose up -d

Каталог `./data` (bind mount, относительно `docker-compose.yml`) содержит и
кэш модели, и шарды БД, и `.auth-token` — это и есть то, что бэкапит borg.
Именованный том сознательно не использован: бэкапить обычный каталог проще,
а состояние читается без docker.

### Эмбеддинги

Считаются **на сервере**, моделью `nomic-embed-text-v1`. `embeddingApiUrl` на
сервере не задаётся, и вот почему:

- внешний API означал бы переиндексацию всех накопленных векторов; при включённых
  task-префиксах это уже давало перекрёстные изменения на малой выборке
  (90→82, 79→76, один запрос 0→60, другой 62→0) — переписывать боевую память
  с непроверяемым результатом нельзя;
- отказ эмбеддинга ударит не потерей, а поломкой: `handleAddMemory` вызывает
  `embedWithTimeout` **до** вставки (`api-handlers.js:314-318`), то есть запись
  не просто теряется, а падает. Это вторая точка отказа вместо одной.

Отсюда инвариант: модель, размерность (768) и `embeddingUseTaskPrefixes` должны
остаться прежними. Смена любого из трёх = обязательная переиндексация.

### Проверка после подъёма

    curl -s localhost:4747/api/health                        # без токена, 200 ok
    TOKEN=$(cat data/.opencode-mem/.auth-token)              # токен в bind mount
    curl -s -H "x-opencode-mem-token: $TOKEN" localhost:4747/api/stats

### HTTPS через Nginx Proxy Manager

TLS на этом хосте уже терминирует Nginx Proxy Manager, поэтому второй
терминатор здесь не нужен и вреден: два слушателя на 80/443 и раздвоение выпуска
сертификатов. Хранилище наружу не публикуется вовсе и говорит по `node:http`
(`serveFetch` в `web-server.js`) только внутри сети.

Proxy Host в NPM:

| поле                  | значение                                       |
| --------------------- | ---------------------------------------------- |
| Domain Names          | `mem.agrohim.info`                             |
| Scheme                | `http`                                         |
| Forward Hostname / IP | `remote-mem`                                   |
| Forward Port          | `4747`                                         |
| Websockets Support    | включить                                       |
| SSL                   | сертификат Let's Encrypt для этого имени       |
| Access List           | **не ограничивать по IP**, авторизация — токен |

NPM должен быть подключён к сети `dockerbee` — иначе имя `remote-mem` не
разрешится и прокси вернёт 502. В compose сеть объявлена как
`external: true`, то есть не создаётся и падает при отсутствии: молча создать
вторую сеть значило бы получить хранилище, до которого ничего не достучится.

Клиент шлёт `x-opencode-mem-token`; заголовки прокси не переписывает. Токен
задаёт авторизацию, а не защиту канала — TLS здесь обязателен, и ограничение по
IP в Access List остаётся осмысленным дополнением, если источники известны.

Токен лежит в томе, а не в репозитории. Каждая машина-клиент получает свой.

## Известное поведение

- При недоступном сервере клиент считает сводку локально и теряет её на этапе
  записи. Фолбэка на локальную БД нет, это осознанное решение владельца
  (потери ~2% знаний приняты).
